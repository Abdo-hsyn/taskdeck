# Decisions & Trade-offs

1. **JWT in HttpOnly cookie (not localStorage).** Why: XSS cannot read the token, `SameSite=Lax` blocks cross-site CSRF on state-changing routes. Alternative rejected: Bearer token in localStorage — simpler CORS, but token theft via XSS is a real risk for a portfolio project meant to be judged on security basics. Note: state-changing routes rely on SameSite + strict CORS origin check; no CSRF token (documented limitation).
2. **Two folders in one repo (`client/`, `server/`) without a workspace tool.** Why: fastest path to a reviewable monorepo; each package has its own `package.json` and CI step. Alternative rejected: Turborepo/pnpm workspaces — nicer, but adds tooling a reviewer must learn before running it; both install with `npm install`.
3. **MySQL via TiDB Cloud Serverless (free tier) instead of SQLite/Mongo/Postgres.** Why: the brief demands "Database"; MySQL is the required engine for this submission, and TiDB Cloud Serverless is MySQL-compatible, free, no credit card, with TLS-only connections. SQLite rejected: no real server / production parity. MongoDB rejected: relational data (projects ↔ members ↔ tasks ↔ comments) fits SQL better. Postgres rejected: MySQL was a hard requirement.
3a. **Prisma 7 schema-engine TLS gotcha (TiDB).** The migration/schema engine reads **`sslaccept=skip-verify`** from `DATABASE_URL` (not `sslmode`, which it ignores for MySQL); `?ssl-mode=REQUIRED` (TiDB's own param name) is ignored by both. The app runtime uses the `mariadb` driver adapter, which reads neither — so `server/src/lib/prisma.ts` parses the URL and builds the pool config itself (`sslaccept=skip-verify` → `ssl: { rejectUnauthorized: false }`, `strict` → `true`). Also: the mariadb pool option is `connectTimeout`, not `connectionTimeout` — using the wrong name silently makes sockets fail after ~1s.
4. **Role-based membership (owner/member) instead of single-user projects.** Why: it makes authorization testable and visible — the classic "server-side authz" signal reviewers look for — at almost no extra scope.
5. **Express 5 + TypeScript + Zod.** Why: validation at the boundary with one error envelope keeps handlers small; Express 5 is current and handles async errors natively (no try/catch soup).
6. **Hosting: Vercel ×2 (client + API), not Render.** Why: Render's API rejected every service-create call with `402 Payment information is required` (web service, static site, explicit `plan: "free"` — all rejected), and the dashboard path produced no service either. Vercel deploys both halves free without a card: `taskdeck-client` (static Vite build) and `taskdeck-api` (Node backend, official pattern: `server.ts` entrypoint default-exporting the Express app; build script runs `prisma generate && prisma migrate deploy && tsc`). Alternative rejected: Koyeb/Adaptable — no reason to move once both projects deployed on Vercel.
6a. **`SameSite=None; Secure` session cookie in production.** Why: client (`taskdeck-client.vercel.app`) and API (`taskdeck-api.vercel.app`) are different registrable domains — a `Lax` cookie is never sent on cross-site XHR, so login would silently fail. `Secure` is mandatory for `SameSite=None`. CSRF stays covered by the CORS origin allowlist + JSON-only body (forces a preflight on state-changing requests). Dev remains `Lax` (same-origin through the Vite proxy, works over http). Note: this supersedes the `SameSite=Lax` wording in decision #1 for production only.
6b. **Interop-safe imports for Vercel's build-time type-checker.** Vercel type-checks Node backends with its own TypeScript options (its checker resolves ESM-style packages — helmet, express-rate-limit — such that their *default* import is the module namespace, non-callable: TS2349, build fails; our `tsconfig.json` passes locally regardless). Fix: use **named imports** where the package declares them (`import { rateLimit } from 'express-rate-limit'`) or read the factory through a typed cast (`helmetNs.default as HelmetFactory` in `server/src/app.ts`). Packages typed `export =` (express, cors, cookie-parser, jsonwebtoken, bcryptjs) are unaffected — their default import works under every flag combination.
7. **Task move = one PATCH with "index in target column" semantics, applied in a single transaction.** Why: the kanban needs exactly one request per drop (drag across columns reorders both sides); the server reads both columns ordered by `position, createdAt`, removes the moved task, re-inserts it at the requested index and renumbers densely — correct even with position gaps left by deletes. The client's `applyMove` mirrors the algorithm exactly, so the optimistic UI and the server agree. Alternatives rejected: sending the full column order (more payload, more to get wrong) and letting the client compute absolute positions (races with concurrent edits).
7a. **Transaction hardening for cold TiDB: 30s timeout / 10s maxWait + skip no-op updates.** Why: TiDB Cloud Serverless sleeps between calls; waking it exceeded Prisma's default 5s transaction timeout (P2028, observed live at 5.3s/6.2s during browser E2E). Each query is also a network round trip, so `applyOrder` now only updates rows whose position actually changed (plus the moved task). Alternatives rejected: dropping the transaction (would allow interleaved moves to corrupt ordering) — the timeout is the correct knob.
8. **Drag & drop with dnd-kit, writes serialized through a client-side queue.** Why: dnd-kit gives mouse + touch + keyboard sensors, an accessible `DragOverlay` and collision detection (`closestCorners`) for free; serializing writes (`enqueue`) prevents rapid drops from racing while optimistic UI keeps it feeling instant, with a rollback `load()` + toast on failure.
